# 백엔드 직무 지원 어필 사례 정리

- 기준 프로젝트: SSUKSSUK 서버
- 목적: 자기소개서, 포트폴리오, 면접 답변에서 사용할 수 있는 백엔드 경험 사례 정리
- 작성 원칙
  - 구조는 `상황 -> 해결방법과 그렇게 생각한 이유 -> 성과` 순서로 통일했습니다.
  - 별도 부하 테스트 수치가 없는 항목은 코드에서 확인 가능한 정책값, 개수, 주기, TTL, timeout, 인덱스/제약, API 개수를 중심으로 정리했습니다.
  - 면접에서는 "실측 성능 개선"과 "구조적 안정성 개선"을 구분해 설명하는 것이 안전합니다.

## 프로젝트 개요

- Spring Boot 3.5.7, Java 17 기반 스마트 식물 관리 서버입니다.
- 주요 기술은 Spring Web, Spring Security, JPA, MySQL, Redis, MQTT, AWS S3 Presigned URL, Firebase FCM, SSE, Actuator, Prometheus입니다.
- 현재 코드 기준 규모는 `@RestController 12개`, REST/SSE/Test 포함 mapping `39개`, Entity `14개`, Repository `14개`입니다.
- 서버의 핵심 책임은 모바일 API 제공뿐 아니라 식물 재배 기기와 MQTT로 통신하고, 센서/이미지/제어 결과를 DB 상태, 알림, 실시간 화면 업데이트로 연결하는 것입니다.

## 1. MQTT 기반 IoT 메시지 수신 파이프라인 분리

### 상황

- 식물 재배 기기에서 센서 데이터, 이미지 분석 결과, 제어 결과, ACK처럼 성격이 다른 MQTT 메시지가 들어오는 구조였습니다.
- 모든 메시지를 하나의 수신 메서드에서 처리하면 토픽 파싱, JSON 파싱, 멱등성 처리, 도메인 로직이 한곳에 섞일 수 있었습니다.
- 특히 MQTT 메시지 종류가 늘어날수록 if/switch 분기가 커지고, 특정 메시지 처리 오류가 다른 채널 처리에도 영향을 줄 위험이 있었습니다.

### 해결방법과 그렇게 생각한 이유

- MQTT 수신 흐름을 `MqttSubscriber -> MqttEnvelope -> MqttDispatchHandler -> MqttMessageHandler` 구조로 분리했습니다.
- `MqttEnvelope`에서 `devices/{serial}/{telemetry|control}/{channel}` 토픽을 공통 포맷으로 파싱하고, serial, direction, channel, payloadJson을 표준화했습니다.
- `MqttDispatchHandler`는 channel 이름으로 handler bean을 찾아 위임하도록 했습니다.
- 실제 도메인 처리는 `SensorTelemetryHandler`, `ImageInferenceTelemetryHandler`, `ActionResultHandler`, `AckInboundHandler`로 나누었습니다.
- 이렇게 나눈 이유는 MQTT 수신부가 transport 계층 역할만 하고, 메시지별 비즈니스 로직은 handler 단위로 독립시키는 편이 확장성과 장애 분석에 유리하다고 판단했기 때문입니다.

### 성과

- 센서, 이미지 추론, 액션 결과, ACK 총 `4개` MQTT 채널 처리 로직을 독립 handler로 분리했습니다.
- 신규 MQTT channel이 추가될 때 dispatcher 구조를 유지한 채 handler bean 추가로 확장할 수 있게 했습니다.
- 토픽 파싱과 payload 파싱을 공통 envelope 단계로 모아 각 handler가 도메인 로직에 집중할 수 있게 했습니다.
- MQTT QoS 1과 자동 재연결 설정을 적용해 IoT 메시지 전달 안정성을 높였습니다.

## 2. Redis 기반 멱등성 처리로 중복 MQTT 메시지 방어

### 상황

- MQTT QoS 1은 메시지 전달 보장을 높이는 대신, 네트워크 재전송이나 클라이언트 재시도 상황에서 같은 메시지가 중복 수신될 수 있습니다.
- 센서 이상 이벤트나 이미지 추론 결과가 중복 처리되면 같은 알림이 여러 번 생성되거나 식물 상태가 반복 갱신될 수 있었습니다.
- DB 저장 이후에만 중복을 확인하면 불필요한 트랜잭션과 쿼리가 발생하고, 외부 알림까지 중복으로 이어질 수 있었습니다.

### 해결방법과 그렇게 생각한 이유

- `RedisIdempotencyService`를 만들고 `serial:msgId`를 멱등 키로 사용했습니다.
- Redis `SET NX`에 해당하는 `setIfAbsent`를 사용해 최초 처리 여부를 원자적으로 판단했습니다.
- 멱등 키 TTL은 `10분`으로 설정했습니다.
- 센서 telemetry, 이미지 inference, action-result 처리 전에 공통적으로 멱등성 검사를 수행했습니다.
- 이 방식을 선택한 이유는 MQTT 중복 메시지는 영구 데이터라기보다 일정 시간 내 재전송 방어가 목적이므로, DB unique constraint보다 Redis TTL 기반의 빠른 gatekeeper가 적합하다고 판단했기 때문입니다.

### 성과

- 센서, 이미지, 액션 결과 등 `3개` 주요 MQTT 처리 경로에 중복 처리 방어를 적용했습니다.
- 중복 메시지는 DB 트랜잭션 진입 전에 차단되도록 했습니다.
- TTL `10분`을 적용해 재전송 방어와 저장공간 관리를 함께 고려했습니다.
- QoS 1 환경에서 "적어도 한 번 전달"의 특성을 서버 쪽 멱등성으로 보완한 경험으로 설명할 수 있습니다.

## 3. MQTT 제어 명령의 ACK 대기 구조 구현

### 상황

- 서버가 기기에 claim, binding, mode 변경 같은 제어 명령을 보낼 때 MQTT publish 성공만으로 API를 성공 처리하면 문제가 있었습니다.
- 실제 기기가 명령을 처리하지 못했는데 서버 DB만 변경되면, 서버 상태와 물리 디바이스 상태가 어긋날 수 있었습니다.
- HTTP API는 동기 응답을 기대하지만 MQTT는 비동기 메시징이므로, 두 통신 모델 사이의 성공 기준을 맞추는 장치가 필요했습니다.

### 해결방법과 그렇게 생각한 이유

- `DeviceControlService`에서 MQTT publish 이후 ACK를 기다리는 구조를 만들었습니다.
- 제어 메시지마다 UUID 기반 `msg_id`를 생성하고, `PendingAckStore`에 `serial + msgId` 기준 `CompletableFuture`를 등록했습니다.
- `AckInboundHandler`는 기기가 보낸 `ref_msg_id`로 pending future를 찾아 완료시킵니다.
- ACK timeout은 `15초`로 설정했습니다.
- ACK 상태가 OK가 아니면 `DEVICE_ACK_FAILED`, 시간 초과면 `DEVICE_ACK_TIMEOUT`으로 변환했습니다.
- pending ACK는 `1초` 주기 sweeper가 만료 정리합니다.
- 이 방식을 선택한 이유는 IoT 제어에서 중요한 것은 "명령을 보냈다"가 아니라 "기기가 실제로 받았고 처리했다"이기 때문입니다. 따라서 ACK 성공을 DB 상태 변경의 전제조건으로 삼았습니다.

### 성과

- claim, mode update, binding bound, binding unbound 등 핵심 기기 제어 `4개` 흐름에 ACK 기반 성공 판정을 적용했습니다.
- ACK timeout `15초`와 pending cleanup `1초` 주기로 무한 대기와 메모리 누수를 방지했습니다.
- 디바이스 응답 실패와 timeout을 서로 다른 비즈니스 에러로 구분할 수 있게 했습니다.
- 비동기 MQTT 통신을 HTTP API의 성공/실패 계약 안으로 끌어온 설계 사례로 어필할 수 있습니다.

## 4. 센서 로그와 이상 이벤트의 open/resolve 모델 분리

### 상황

- 센서가 주기적으로 이상 상태를 보내는 경우, 매번 새 이벤트와 알림을 만들면 사용자에게 같은 이상 알림이 반복될 수 있었습니다.
- 반대로 회복 신호가 왔을 때 기존 이상 이벤트를 종료하지 못하면 식물 상태가 계속 문제 상태로 남을 수 있었습니다.
- 모든 센서 측정값을 남기는 로그와 사용자에게 의미 있는 이상 상태 이벤트는 목적이 달랐습니다.

### 해결방법과 그렇게 생각한 이유

- 모든 센서 데이터는 `SensorLog`에 저장하되, 이상 상태는 `SensorEvent`의 open/resolve 상태 전이로 모델링했습니다.
- `ANOMALY_DETECTED`가 들어오면 같은 식물과 센서 타입의 open event를 먼저 찾습니다.
- open event가 없을 때만 `SensorEvent.open()`으로 새 이벤트를 만들고, 이미 열려 있으면 `lastLog`만 갱신합니다.
- `RECOVERY_DONE`이 들어오면 open event를 찾아 resolve 처리합니다.
- 알림 저장과 식물 상태 갱신은 같은 트랜잭션 안에서 처리하고, FCM 발송은 commit 이후에 실행되도록 했습니다.
- 이렇게 설계한 이유는 로그는 관측 이력을 모두 보존해야 하지만, 이벤트는 사용자에게 의미 있는 상태 변화만 표현해야 하기 때문입니다.

### 성과

- 주기 센서 로그와 이상 이벤트를 분리해 데이터 의미를 명확히 했습니다.
- 같은 이상 상태가 반복될 때 중복 이벤트와 중복 알림 생성을 방지했습니다.
- 이벤트 시작/종료 시각을 남길 수 있는 구조를 만들었습니다.
- 센서 이상/회복 알림을 DB commit 이후 발송하도록 해 저장 데이터와 외부 push 사이의 정합성을 높였습니다.

## 5. S3 Presigned URL 기반 이미지 업로드 파이프라인

### 상황

- 재배 기기가 식물 사진을 서버로 직접 업로드하면 서버가 이미지 바이너리를 중계해야 하므로 네트워크와 메모리 부담이 커질 수 있었습니다.
- 기기별, 식물별, 촬영 시점별로 이미지를 체계적으로 저장해야 성장 히스토리와 AI 추론 결과를 연결할 수 있었습니다.
- 이미지 업로드 권한은 필요할 때 짧게 위임하고, 서버는 업로드 경로와 메타데이터 계약을 관리하는 편이 안전했습니다.

### 해결방법과 그렇게 생각한 이유

- 서버가 S3 Presigned PUT URL을 생성하고 MQTT로 기기에 전달하는 구조를 만들었습니다.
- 운영 스케줄은 매일 `06:00`, `18:00` 두 번 실행됩니다.
- 연결된 식물 바인딩을 조회한 뒤 식물별 업로드 URL 발행 작업을 `@Async("uploadUrlExecutor")`로 분산했습니다.
- 식물당 `TOP`, `SIDE` 두 개 이미지 URL을 생성합니다.
- S3 object key는 `plants/{plantId}/images/yyyy/MM/dd/{slot}/{view}.jpg` 형태로 구성했습니다.
- Presigned URL 기본 만료 시간은 `900초(15분)`이고, Content-Type은 `image/jpeg`로 고정했습니다.
- 이 방식을 선택한 이유는 API 서버가 이미지 바이너리를 직접 받는 것보다 S3에 직접 업로드하게 하는 편이 서버 부하와 권한 노출 시간을 줄일 수 있기 때문입니다.

### 성과

- 하루 `2회` 정기 이미지 수집 파이프라인을 구성했습니다.
- 식물당 스케줄 1회에 `TOP/SIDE 2개` 업로드 URL을 발급하도록 했습니다.
- Presigned URL TTL `15분`으로 업로드 권한 노출 시간을 제한했습니다.
- 업로드 URL 생성 executor를 core `10`, max `30`, queue `100`으로 구성해 다수 식물 대상 발행 작업을 병렬 처리할 수 있게 했습니다.
- 서버가 이미지 파일을 직접 중계하지 않는 구조로 API 서버의 네트워크/메모리 부담을 줄였습니다.

## 6. 이미지 AI 추론 결과 저장 및 성장 그래프 집계

### 상황

- 기기에서 이미지 분석 결과가 들어오면 단순히 최신값만 저장하는 것으로는 부족했습니다.
- 사용자는 최근 성장 추이를 봐야 하고, 이미지 이상 징후가 있으면 알림도 받아야 했습니다.
- AI가 px 단위로 보낸 높이와 너비를 사용자에게 이해 가능한 cm 단위로 보정해야 했습니다.
- 또한 잘못된 plantId나 다른 기기의 serial로 추론 결과가 들어오면 데이터가 오염될 수 있었습니다.

### 해결방법과 그렇게 생각한 이유

- `ImageInferenceService`에서 이미지 저장, 추론 저장, 식물 상태 갱신, 알림 생성을 하나의 처리 흐름으로 연결했습니다.
- `plantId + serial` 기준 active binding 여부를 검증해 임의 기기가 다른 식물 데이터를 넣지 못하게 했습니다.
- 이미지 URL은 `PlantImage`, 추론 결과는 `ImageInference`에 분리 저장했습니다.
- 높이는 `15.0 / 865.0`, 너비는 `10.0 / 344.0` 보정 계수로 cm 단위 변환 후 소수점 1자리로 반올림했습니다.
- confidence가 없거나 anomaly/height/width 중 최소 1개도 없으면 저장하지 않도록 validation을 두었습니다.
- 최근 `14일` 성장 그래프는 날짜별 마지막 inference 값을 native query로 조회했습니다.
- confidence `70 이상`이고 anomaly `5 이상`이면 이미지 이상 알림을 생성하고 commit 이후 FCM을 발송했습니다.
- 이렇게 설계한 이유는 원천 이미지와 AI 추론 결과의 생명주기가 다르기 때문입니다. 둘을 분리하면 추후 모델이 바뀌거나 같은 이미지에 재추론을 붙일 때 확장하기 쉽습니다.

### 성과

- 이미지 저장, AI 추론 저장, 식물 상태 갱신, 이상 알림을 하나의 파이프라인으로 구성했습니다.
- 최근 `14일` 성장 그래프 데이터를 API로 제공할 수 있게 했습니다.
- px 기반 AI 결과를 cm 단위 도메인 값으로 보정해 사용자에게 이해 가능한 데이터로 변환했습니다.
- active binding 검증과 Redis 멱등성 검사를 통해 잘못된 기기 데이터와 중복 추론 결과 유입을 방어했습니다.

## 7. SSE + Redis Pub/Sub 기반 실시간 홈 화면 업데이트

### 상황

- 센서 데이터나 이미지 분석 결과로 식물 상태가 바뀌면 홈 화면도 즉시 갱신되어야 했습니다.
- 클라이언트가 polling을 사용하면 불필요한 API 요청이 늘고, 상태 변경 반영 지연도 생길 수 있었습니다.
- 서버가 여러 인스턴스로 확장될 경우, 특정 인스턴스에서 발생한 상태 변경을 다른 인스턴스의 SSE 연결 사용자에게 전달하기 어렵다는 문제가 있었습니다.

### 해결방법과 그렇게 생각한 이유

- 식물 상태 변경 시 `PlantStatusUpdatedEvent`를 발행하고, SSE 서비스가 transaction commit 이후 Redis Pub/Sub으로 plantId를 publish하도록 했습니다.
- SSE 연결은 userId 기준 `ConcurrentHashMap<Long, SseEmitter>`로 관리했습니다.
- 새 연결이 들어오면 기존 emitter를 complete 처리해 사용자당 하나의 활성 연결만 유지했습니다.
- SSE timeout은 `1시간`으로 설정했습니다.
- Redis channel은 `plant-status-update`로 두고, 메시지를 받은 서버가 해당 plantId의 main plant status를 조회한 뒤 연결된 user에게 `update` event를 전송합니다.
- 이 구조를 선택한 이유는 DB commit 전에 화면 push가 나가면 사용자가 실제 저장되지 않은 상태를 볼 수 있기 때문입니다. 또한 Redis Pub/Sub을 사이에 두면 상태 변경 서버와 SSE 연결 서버가 달라도 전파할 수 있습니다.

### 성과

- 홈 화면 실시간 업데이트를 polling 없이 SSE로 제공했습니다.
- SSE 연결 timeout `1시간`으로 장시간 구독을 지원했습니다.
- Redis Pub/Sub을 적용해 다중 서버 확장 시에도 상태 변경 전파가 가능한 구조를 만들었습니다.
- 상태 변경 push를 commit 이후로 제한해 화면 데이터와 DB 상태의 정합성을 높였습니다.

## 8. JWT + Refresh Token Rotation 기반 인증 설계

### 상황

- 모바일 앱에서 access token만 길게 유지하면 탈취 위험이 커질 수 있습니다.
- refresh token을 계속 재사용하면 유출된 refresh token으로 장기간 재발급이 가능해집니다.
- 탈퇴 사용자가 기존 token으로 API를 호출하는 것도 서버에서 막아야 했습니다.

### 해결방법과 그렇게 생각한 이유

- JWT access token과 DB 저장 refresh token을 분리하고, refresh 시 기존 refresh token을 revoke하는 rotation 구조를 적용했습니다.
- access token 만료 시간은 `900초(15분)`로 설정했습니다.
- refresh token 만료 시간은 `1,209,600초(14일)`로 설정했습니다.
- refresh 요청 시 JWT 서명, issuer, type을 검증하고 DB 저장 여부와 revoked 여부를 확인합니다.
- refresh 성공 시 기존 token을 revoke하고 새 access/refresh token을 발급합니다.
- logout 시 사용자 refresh token을 삭제하고, withdraw 시 soft delete와 refresh token revoke를 함께 수행합니다.
- JWT filter에서는 access token의 type과 탈퇴 사용자 여부를 다시 확인합니다.
- 이 구조를 선택한 이유는 stateless access token의 장점은 유지하되, 장기 세션 역할을 하는 refresh token은 서버가 통제할 수 있어야 하기 때문입니다.

### 성과

- access token `15분`, refresh token `14일` 정책을 분리했습니다.
- refresh token 재사용을 막기 위해 refresh 시 기존 token을 revoke했습니다.
- logout/withdraw 시 서버 저장 refresh token을 제거 또는 revoke해 세션 통제력을 확보했습니다.
- `39개` mapping에 공통 JWT filter 기반 인증 구조를 적용했습니다.

## 9. FCM 토큰 관리와 유효하지 않은 토큰 자동 정리

### 상황

- 모바일 push token은 앱 재설치, 로그아웃, 기기 변경 등으로 자주 바뀝니다.
- 유효하지 않은 token을 계속 보관하면 알림 발송 실패가 반복되고, 운영 로그 노이즈가 늘어납니다.
- 한 사용자가 여러 모바일 기기를 사용할 수 있고, 반대로 같은 기기의 token이 갱신될 수도 있었습니다.

### 해결방법과 그렇게 생각한 이유

- `PushService`에서 모바일 deviceId 기준으로 FCM token을 upsert하도록 했습니다.
- `fcm_token` 테이블은 `device_id`에 unique constraint를 두고, user_id, token, device_id에 index를 두었습니다.
- token 등록 시 같은 mobileDeviceId가 있으면 token만 update하고, 신규 deviceId면 row를 생성합니다.
- 로그인 시 mobileDeviceId가 있으면 기존 push token row에 userId를 연결하고, 로그아웃 시 userId를 null 처리합니다.
- FCM 발송 중 `MessagingErrorCode.UNREGISTERED`가 발생하면 해당 token을 삭제합니다.
- 이 방식을 선택한 이유는 push token의 생명주기가 사용자 계정보다 모바일 설치 단위에 가깝기 때문입니다. deviceId 기준으로 관리하면 token 변경으로 row가 무한히 늘어나는 문제를 줄일 수 있습니다.

### 성과

- deviceId 기준 FCM token upsert 구조를 구현했습니다.
- 로그인/로그아웃과 push token의 userId 매핑을 연동했습니다.
- invalid FCM token을 자동 삭제해 반복 실패를 줄이는 구조를 만들었습니다.
- 알림 이력은 DB에 남기고, push 발송 실패는 외부 시스템 실패로 분리해 대응할 수 있게 했습니다.

## 10. 식물-디바이스 바인딩 정합성 확보

### 상황

- 스마트 화분 서비스에서는 사용자, 식물, 디바이스의 연결 상태가 핵심입니다.
- 다른 사용자의 디바이스가 바인딩되거나, 이미 다른 식물에 연결된 디바이스가 중복 연결되면 센서 데이터와 제어 명령이 잘못된 식물로 흘러갈 수 있습니다.
- IoT 시스템에서는 서버 DB 상태와 물리 디바이스 상태가 어긋나는 순간 장애 원인 파악이 어려워집니다.

### 해결방법과 그렇게 생각한 이유

- 바인딩 검증과 상태 변경 책임을 `PlantBindingService`, `DeviceClaimService`, `DeviceBindingValidator`로 분리했습니다.
- bind 전 디바이스 소유자와 중복 pairing 여부를 검증했습니다.
- binding/unbinding 시 MQTT 명령을 보내고 ACK 성공 후 DB 상태를 변경했습니다.
- bind 성공 시 기존 main plant를 해제하고 새로 연결한 plant를 main으로 설정했습니다.
- MQTT 센서 수신 시 serial과 plantId의 active binding 여부를 검증해 비정상 메시지를 차단했습니다.
- claim/unclaim, bind/unbind는 별도 transaction인 `REQUIRES_NEW`로 처리해 중간 상태를 명확히 했습니다.
- 이렇게 판단한 이유는 IoT 제어에서는 "검증 -> 디바이스 ACK -> DB 변경" 순서를 지켜야 서버 상태와 실제 기기 상태의 불일치를 줄일 수 있기 때문입니다.

### 성과

- 디바이스 소유권, 중복 연결, active binding 검증을 서버 단에서 수행했습니다.
- claim, bind, unbind, mode 변경을 MQTT ACK 기반으로 통제했습니다.
- 센서 데이터 수신 시 plantId와 device serial 기반 검증을 추가해 잘못된 데이터 유입을 방어했습니다.
- 식물 목록 조회에서는 species/device fetch join을 사용해 N+1 가능성을 줄였습니다.

## 11. 홈/히스토리 조회 API의 읽기 모델 최적화

### 상황

- 홈 화면과 히스토리 화면은 사용자가 자주 접근하는 읽기 중심 API입니다.
- Entity 관계를 단순 lazy loading에 맡기면 N+1 문제가 발생하거나, 화면에 필요한 데이터를 만들기 위해 여러 번 쿼리해야 할 수 있었습니다.
- 그래프 API는 누락된 날짜를 클라이언트가 추론하게 두면 프론트엔드 구현이 복잡해질 수 있었습니다.

### 해결방법과 그렇게 생각한 이유

- 조회 목적에 맞는 repository query를 별도로 작성했습니다.
- 홈 조회는 main plant status, userPlant, characterCode를 fetch join으로 한 번에 가져옵니다.
- 식물 목록은 species와 device를 fetch join으로 조회합니다.
- 최근 `14일` 이미지는 KST 기준 `[from, to)` 범위를 계산해 조회합니다.
- 성장 그래프는 날짜별 마지막 inference를 native query로 집계합니다.
- 센서 알림 그래프는 최근 `14일`을 고정 길이 배열로 만들고, 데이터가 없는 날짜도 0으로 반환합니다.
- 이 방식을 선택한 이유는 읽기 API는 화면 요구사항에 맞춰 쿼리를 설계해야 응답 형태가 안정적이고 클라이언트 복잡도가 줄어든다고 판단했기 때문입니다.

### 성과

- 최근 `14일` 성장 그래프, 센서 알림 그래프, 이미지 조회를 제공했습니다.
- 홈 화면 조회에서 fetch join으로 main plant status와 캐릭터 이미지를 함께 조회했습니다.
- 그래프 응답을 고정 `14개` 포인트 기준으로 구성해 클라이언트 렌더링 복잡도를 낮췄습니다.
- KST 기준 날짜 범위를 명시해 사용자 지역 기준의 일별 히스토리를 안정적으로 제공했습니다.

## 12. 운영 관측성과 배포 환경 분리

### 상황

- 서버가 IoT 메시지, DB 트랜잭션, Redis, S3, FCM, MQTT를 함께 다루기 때문에 장애 발생 시 원인 파악이 어려울 수 있었습니다.
- 개발 환경과 운영 환경의 SQL 출력, web/security log 정책을 다르게 가져갈 필요가 있었습니다.
- 배포 후 서버가 살아 있는지, HTTP latency가 어떤지 확인할 수 있는 관측 기반이 필요했습니다.

### 해결방법과 그렇게 생각한 이유

- Spring profile과 Actuator/Prometheus 설정을 적용했습니다.
- `application-dev.properties`와 `application-prod.properties`로 환경별 설정을 분리했습니다.
- 운영 profile에서는 SQL 출력과 상세 web/security log를 줄였습니다.
- Actuator endpoint로 `health`, `info`, `prometheus`, `metrics`를 노출했습니다.
- Micrometer Prometheus registry를 추가했습니다.
- HTTP server request percentile histogram을 활성화했습니다.
- 이 방식을 선택한 이유는 IoT 서버는 비동기 이벤트가 많아 단순 로그만으로 지연이나 장애 징후를 파악하기 어렵기 때문입니다. metric endpoint를 열어두면 추후 대시보드와 알림으로 연결할 수 있습니다.

### 성과

- 개발/운영 profile을 분리해 환경별 로그 정책을 다르게 가져갈 수 있게 했습니다.
- Prometheus metric endpoint를 제공해 모니터링 연동 기반을 마련했습니다.
- HTTP 요청 latency histogram을 활성화해 p95/p99 같은 지표 분석이 가능한 구조를 만들었습니다.
- Actuator health endpoint로 배포 후 상태 확인 자동화 기반을 확보했습니다.

## 13. 공통 API 응답과 전역 예외 처리로 REST API 계약 표준화

### 상황

- 기능이 늘어날수록 controller마다 성공/실패 응답 형식이 달라지면 모바일 클라이언트가 API별로 다른 예외 처리를 해야 하는 문제가 생길 수 있었습니다.
- 입력값 검증 실패, JSON 파싱 실패, 인증 실패, 비즈니스 예외가 서로 다른 형태로 내려가면 프론트엔드와 QA가 장애 원인을 파악하기 어려워질 수 있었습니다.
- Spring Security filter chain에서 발생하는 인증/인가 오류도 일반 API 오류와 같은 응답 계약으로 맞출 필요가 있었습니다.

### 해결방법과 그렇게 생각한 이유

- 공통 응답 wrapper인 `ApiResponse<T>`를 만들고 성공 응답은 `success=true, data`, 실패 응답은 `success=false, error(code, message)` 형태로 통일했습니다.
- `GlobalExceptionHandler`에서 `CustomException`, `MethodArgumentNotValidException`, `HttpMessageNotReadableException`, 일반 `Exception`을 한곳에서 처리하도록 했습니다.
- `ErrorCode` enum에 HTTP status, 비즈니스 에러 코드, 기본 메시지를 모아 controller/service 계층이 문자열을 직접 만들지 않도록 했습니다.
- `SecurityConfig`의 `authenticationEntryPoint`, `accessDeniedHandler`에서도 `ApiResponse.fail()`을 JSON으로 내려 인증/인가 실패 응답까지 같은 계약을 사용하게 했습니다.
- 이렇게 설계한 이유는 REST API의 안정성은 기능 구현뿐 아니라 클라이언트가 예측 가능한 응답 계약을 받는 데서 나오기 때문입니다. 예외 처리와 응답 포맷을 횡단 관심사로 분리하면 controller는 정상 흐름에 집중할 수 있습니다.

### 성과

- `ApiResponse<T>` 기반으로 controller와 security exception 응답을 같은 형태로 맞췄습니다.
- `25개` ErrorCode를 enum으로 관리해 비즈니스 예외와 HTTP status 매핑을 명확히 했습니다.
- `@Valid` 검증 실패는 field 단위 메시지로 조합하고, JSON 파싱 실패는 별도 메시지로 반환하도록 했습니다.
- controller/service 곳곳에서 직접 `ResponseEntity`나 에러 JSON을 조립하지 않아도 되는 구조를 만들었습니다.

## 14. Java record DTO와 Bean Validation 기반 요청/응답 모델링

### 상황

- 모바일 API, MQTT 테스트 API, 관리자 API처럼 요청/응답 모델이 늘어나면 DTO가 불필요하게 mutable해지거나 Entity가 API 응답에 직접 노출될 위험이 있었습니다.
- 필수값, 이메일 형식, 비밀번호 규칙, enum 입력값 같은 기본 검증을 서비스 내부에서 수동으로 처리하면 중복 코드가 늘고 검증 누락 가능성이 생길 수 있었습니다.
- API boundary에서 잘못된 요청을 빠르게 차단해야 service 계층은 도메인 규칙과 상태 변경에 집중할 수 있었습니다.

### 해결방법과 그렇게 생각한 이유

- 요청/응답 DTO를 Java `record`로 정의해 API payload를 불변 값 객체처럼 다루도록 했습니다.
- `SignUpRequest`, `LoginRequest`, `PasswordUpdateRequest`, `ModeChangeRequest`, `PushTokenRequest`, `CreatePlantRequest` 등에 `@NotBlank`, `@NotNull`, `@Email`, `@Size`, `@Pattern` 기반 Bean Validation을 적용했습니다.
- controller에서는 `@Valid @RequestBody`로 request DTO 검증을 수행하고, 실패 응답은 `GlobalExceptionHandler`가 공통 처리하도록 연결했습니다.
- 응답도 `LoginResponse`, `TokenRefreshResponse`, `HomeResponse`, `PlantHistoryResponse`처럼 화면/기능 단위 DTO로 분리해 Entity 구조 변경이 곧바로 API 계약 변경으로 번지지 않도록 했습니다.
- 이 방식을 선택한 이유는 Java 17의 record가 DTO의 의도를 간결하게 드러내고, Spring Validation과 결합했을 때 API 입력 검증을 선언적으로 관리할 수 있기 때문입니다.

### 성과

- 현재 코드 기준 `16개` record 기반 DTO/공통 응답 모델을 사용하고 있습니다.
- DTO와 controller 경계에 `30개` validation annotation을 적용해 필수값, 형식, 길이, 패턴 검증을 API 진입 지점에서 처리했습니다.
- Entity와 API 응답 모델을 분리해 내부 도메인 구조와 외부 API 계약의 결합도를 낮췄습니다.
- 서비스 계층의 조건문을 줄이고, 잘못된 요청은 Spring MVC validation 단계에서 일관된 실패 응답으로 변환되도록 했습니다.

## 15. 인증 핵심 흐름의 단위 테스트와 회귀 방어

### 상황

- 인증 로직은 refresh token rotation, access/refresh token type 구분, 탈퇴 사용자 차단처럼 작은 조건 하나가 보안 문제로 이어질 수 있는 영역입니다.
- 특히 refresh token 재발급은 동시 요청이 들어왔을 때 이미 revoke된 token이 다시 통과하면 rotation 정책이 깨질 수 있었습니다.
- JWT filter는 access token만 인증 객체를 만들고 refresh token은 API 인증에 사용할 수 없어야 하므로, token type 검증이 실제 filter 동작에서도 보장되는지 확인할 필요가 있었습니다.

### 해결방법과 그렇게 생각한 이유

- `UserServiceTest`에서 이미 다른 요청이 refresh token을 revoke한 상황을 mock으로 구성하고, `revokeIfActive()` 결과가 `0`이면 `UNAUTHORIZED`로 실패하는지 검증했습니다.
- 같은 테스트에서 실패 시 `jwtTokenProvider.getUserId()`가 호출되지 않는지도 확인해, 폐기된 token으로 사용자 조회와 새 토큰 발급 흐름에 진입하지 못하게 했습니다.
- `JwtAuthenticationFilterTest`에서는 실제 `JwtTokenProvider`로 access token과 refresh token을 생성한 뒤 filter를 통과시켜 `SecurityContextHolder` 인증 객체 생성 여부를 검증했습니다.
- access token은 API 요청 인증에 성공하고, refresh token은 유효한 JWT여도 인증 객체를 만들지 않는다는 회귀 테스트를 추가했습니다.
- 이렇게 테스트한 이유는 인증 로직은 구현 의도만 문서화하는 것보다 실패해야 하는 경계를 테스트로 고정해두는 편이 유지보수 중 실수를 줄이는 데 효과적이기 때문입니다.

### 성과

- 현재 인증 관련 단위 테스트 `3개`로 refresh token 재사용 방어와 JWT filter token type 검증을 확인하고 있습니다.
- Mockito 기반 service test와 Spring mock request/response 기반 filter test를 함께 사용해 순수 비즈니스 로직과 servlet filter 동작을 분리 검증했습니다.
- refresh token rotation의 핵심 조건인 "활성 token 1건만 revoke되어야 재발급 진행" 규칙을 테스트로 고정했습니다.
- Java/Spring Security 기반 인증 코드를 테스트 가능한 단위로 나누고, 보안 회귀를 조기에 발견할 수 있는 기반을 마련했습니다.

## 지원서/면접에서 강조하기 좋은 축

### IoT 메시징 안정성

- MQTT QoS 1 환경에서 Redis 멱등성 키와 ACK 대기 구조를 적용해 중복 처리와 서버-디바이스 상태 불일치 문제를 줄였습니다.
- `serial + msgId` 기반 pending ACK와 `ref_msg_id` 기반 완료 처리로 비동기 MQTT를 HTTP API의 성공/실패 계약에 연결했습니다.
- claim, bind, unbind, mode 변경에서 ACK 성공 이후 DB 상태를 변경하도록 설계했습니다.

### 데이터 정합성

- 센서 로그와 이상 이벤트를 분리하고 open/resolve 모델로 설계해 반복 알림을 방지하면서 상태 변화 추적성을 확보했습니다.
- DB commit 이후 FCM/SSE를 발송하도록 설계해 사용자 알림과 저장 데이터의 정합성을 높였습니다.
- active binding 검증으로 잘못된 기기나 식물 ID를 가진 MQTT 데이터 유입을 방어했습니다.

### 확장 가능한 백엔드 구조

- MQTT handler를 channel 단위로 분리해 신규 telemetry 메시지 추가 비용을 낮췄습니다.
- S3 Presigned URL을 MQTT로 전달하는 구조로 이미지 업로드를 서버 중계 없이 처리했습니다.
- Redis Pub/Sub과 SSE를 결합해 다중 서버 환경에서도 실시간 홈 화면 업데이트가 가능한 구조를 만들었습니다.

### 보안과 운영

- Access Token 15분, Refresh Token 14일 정책과 Refresh Token Rotation으로 모바일 인증 세션의 통제력을 높였습니다.
- 탈퇴 사용자 차단, logout/withdraw 시 refresh token 정리, FCM invalid token 삭제를 통해 운영 중 남는 세션과 토큰을 관리했습니다.
- Actuator/Prometheus 설정으로 배포 후 health, metrics, latency 관측 기반을 마련했습니다.

### Java / Spring Boot 개발 역량

- Java 17 record DTO와 Spring Bean Validation을 활용해 API 요청/응답 모델을 명확히 분리하고, 잘못된 입력을 controller 진입 지점에서 일관되게 차단했습니다.
- `ApiResponse<T>`, `ErrorCode`, `GlobalExceptionHandler`로 성공/실패 응답 계약을 표준화해 controller가 정상 흐름에 집중할 수 있는 구조를 만들었습니다.
- Spring Security의 `OncePerRequestFilter`와 `SecurityFilterChain`을 사용해 stateless JWT 인증을 구성하고, 인증/인가 실패도 공통 JSON 응답으로 맞췄습니다.
- JUnit 5, AssertJ, Mockito, Spring mock request/response를 사용해 refresh token rotation과 JWT filter의 token type 검증을 단위 테스트로 고정했습니다.
